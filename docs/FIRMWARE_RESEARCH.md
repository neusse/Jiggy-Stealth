# Jiggy-Stealth firmware research

Verified against the linked Adafruit product, the Adafruit TinyUSB Arduino example, TinyUSB examples, and the Pico-PIO-USB project on 2026-10-25. These notes establish firmware feasibility and constraints; they are not a claim that firmware was built or tested on the physical board.

## Findings

- Product 5723 uses the RP2040's native USB connection as a device connection to the computer and Pico-PIO-USB on PIO to implement the second, USB-A host port. Its USB-A data pins are GPIO16 (D+) and GPIO17 (D-); host 5 V is from an enabled TPS61023 boost converter on GPIO18, with a stated 1 A peak output and a 500 mA resettable fuse. The RP2040 has two cores, 264 KB RAM and 8 MB flash. [Adafruit product page](https://www.adafruit.com/product/5723) · [Adafruit board guide](https://learn.adafruit.com/adafruit-feather-rp2040-with-usb-type-a-host)
- Adafruit's `hid_remapper` Arduino sketch is a useful dual-role starting point, but it is a **keyboard** remapper: it declares a keyboard-only device report descriptor, only requests reports from boot-keyboard host interfaces, treats reports of exactly 8 bytes as keyboards, and sends keyboard reports. It does not forward a mouse. Its shift operation changes the keyboard modifier in an incoming keyboard report; it does not send an independent timed Shift press. [Current sketch](https://github.com/adafruit/Adafruit_TinyUSB_Arduino/blob/master/examples/DualRole/HID/hid_remapper/hid_remapper.ino)
- That sketch explicitly asks the RP2040 to run the host on core 1: `setup1()` configures PIO USB and starts `USBHost`, and `loop1()` services `USBHost.task()`. The native-USB device stack is set up on the Arduino/main core. This matches the intended host-plus-device split. [Adafruit sketch](https://github.com/adafruit/Adafruit_TinyUSB_Arduino/blob/master/examples/DualRole/HID/hid_remapper/hid_remapper.ino) · [Adafruit guide](https://learn.adafruit.com/adafruit-feather-rp2040-with-usb-type-a-host)
- The Adafruit sketch documents 120 MHz or 240 MHz for the PIO-USB RP2040 host. The Pico-PIO-USB TinyUSB host-plus-device example explains that the default 125 MHz is unsuitable, sets the system clock to 120 MHz (a multiple of 12 MHz), runs PIO host tasks on core 1, and runs the native USB device stack on core 0. Use 120 MHz as the initial known configuration. [Adafruit sketch](https://github.com/adafruit/Adafruit_TinyUSB_Arduino/blob/master/examples/DualRole/HID/hid_remapper/hid_remapper.ino) · [PIO-USB dual-role example](https://github.com/sekigon-gonnoc/Pico-PIO-USB/blob/main/examples/host_hid_to_device_cdc/host_hid_to_device_cdc.c)
- The upstream Pico-PIO-USB project reports full-speed host, low-speed host, hub support, and full-speed device support. Its dual-role HID example receives boot mouse and keyboard reports from the host port, but prints mouse data to CDC; changing this example to relay reports as HID input is a close reference, though the Adafruit TinyUSB Arduino example is likely the smoother Arduino starting point. [PIO-USB README](https://github.com/sekigon-gonnoc/Pico-PIO-USB/blob/main/README.md) · [PIO-USB dual-role example](https://github.com/sekigon-gonnoc/Pico-PIO-USB/blob/main/examples/host_hid_to_device_cdc/host_hid_to_device_cdc.c)
- Both the Adafruit sketch and the PIO-USB example re-request a host report after processing it. The Adafruit code blocks in a loop waiting for the device HID endpoint to become ready and explicitly recommends queueing instead. For a mouse relay, never wait for USB device readiness inside the host report callback: copy/normalize the host report into a bounded core-to-core queue, request the next host report, and let core 0 send when the device endpoint is ready. Track button state and release transitions as well as x/y/wheel deltas. Define queue-overflow behavior so pressure cannot deadlock the host task. [Adafruit sketch](https://github.com/adafruit/Adafruit_TinyUSB_Arduino/blob/master/examples/DualRole/HID/hid_remapper/hid_remapper.ino) · [PIO-USB dual-role example](https://github.com/sekigon-gonnoc/Pico-PIO-USB/blob/main/examples/host_hid_to_device_cdc/host_hid_to_device_cdc.c)
- A mouse-side custom/vendor report descriptor is not automatically a boot mouse report. The reference examples only recognize boot-protocol keyboard/mouse, and TinyUSB documents descriptor parsing for common/simple reports and a finite enumeration report-descriptor buffer. Start by supporting a standard boot-protocol mouse. Add descriptor-aware report decoding only if the actual mouse needs it; a USB HID bridge does not automatically reproduce vendor-specific mouse controls, identity, configuration, lighting, or proprietary features. [PIO-USB example](https://github.com/sekigon-gonnoc/Pico-PIO-USB/blob/main/examples/host_hid_to_device_cdc/host_hid_to_device_cdc.c) · [Adafruit sketch](https://github.com/adafruit/Adafruit_TinyUSB_Arduino/blob/master/examples/DualRole/HID/hid_remapper/hid_remapper.ino)
- TinyUSB's HID composite example provides a proven report-descriptor pattern combining distinct report-ID keyboard and mouse reports in one HID interface, and demonstrates relative mouse deltas and key-release reports. This fits the desired synthetic mouse movement and separate left-Shift press/release. [TinyUSB composite HID descriptor](https://github.com/hathach/tinyusb/blob/master/examples/device/hid_composite/src/usb_descriptors.c) · [TinyUSB composite HID sender](https://github.com/hathach/tinyusb/blob/master/examples/device/hid_composite/src/main.c)

## Recommended firmware shape

Keep the Adafruit Arduino/Pico-PIO-USB dual-role structure, but change its device descriptor to expose mouse and keyboard HID reports. On host mount, accept the mouse interface and request reports. Normalize each supported boot mouse report; forward button state and relative movement, vertical scroll, and horizontal pan when available. Queue reports without blocking in the host callback, and have the device-side loop drain the queue whenever its HID endpoint is ready.

Run optional behavior on the device core and default it to off. A button-controlled mode can select off, small mouse movement, or an explicit left-Shift pulse; a configurable idle threshold resets on real mouse activity. To send Shift, issue a keyboard report with left Shift down followed by a separate empty keyboard report to release it. Do not inject Shift by modifying the mouse packet or by holding Shift indefinitely. Keep synthetic mouse reports in the same output path as real mouse reports so report/button ordering is defined.

The biggest compatibility decision is the target mouse. Standard wired USB mice and receiver dongles using a boot mouse protocol should be the initial target. A high-button-count or vendor-specific gaming mouse may need report-descriptor parsing and explicit field mapping. Product tests should check ordinary motion, all supported buttons, wheel/pan, long idle then synthetic behavior, immediate resumption of physical input, disconnect/reconnect, mode changes, and a long Shift pulse sequence that always emits key-up.

## M305 receiver follow-up

The M305 connects through its USB receiver, and Logitech documents multiple receiver variants: only an M305 marked Unifying-ready is compatible with the replacement Unifying receiver it identifies. Identify and enumerate the reference actual dongle; do not hard-code a receiver VID/PID or infer Unifying support from the M305 model alone. This research has not enumerated the reference physical receiver, so it does not establish its interface count, protocol mode, report IDs, or field layout. [Logitech receiver guidance](https://support.logi.com/hc/en-us/articles/360023384373-Purchasing-a-replacement-USB-receiver-for-my-M305-mouse) · [M305 quick-start sheet](https://download01.logitech.com/support/12864.1.0.pdf)

For the requested tilt/horizontal scroll, treat boot mouse support as a first diagnostic only. HID 1.11 guarantees the first three bytes of a boot mouse report follow the boot format; optional appended bytes may exist but a BIOS ignores them. The report descriptor defines the full report-mode fields and any report IDs. TinyUSB's host stack can enumerate HID interfaces separately and supplies each interface's report descriptor; its parser can identify basic usage and report IDs, and the official generic-HID example dispatches on those IDs. That parser/example does not unpack arbitrary field bit offsets, widths, or signedness: its generic mouse path still assumes `hid_mouse_report_t`. The actual M305 receiver descriptor must therefore be captured and its mouse fields decoded explicitly if they use Report protocol or Report IDs. For a boot-capable receiver interface, verify/use Report protocol if needed for wheel and AC Pan; for a non-boot HID interface, TinyUSB already uses report mode. [USB-IF HID 1.11](https://www.usb.org/sites/default/files/documents/hid1_11.pdf) · [TinyUSB host HID implementation](https://github.com/hathach/tinyusb/blob/master/src/class/hid/hid_host.c) · [TinyUSB official generic HID host example](https://github.com/hathach/tinyusb/blob/master/examples/host/cdc_msc_hid/src/hid_app.c)

**Example choice:** Adafruit's [`hid_mouse_log_filter`](https://github.com/adafruit/Adafruit_TinyUSB_Arduino/blob/master/examples/DualRole/HID/hid_mouse_log_filter/hid_mouse_log_filter.ino) is the better Arduino host-flow starting point than the keyboard-only `hid_remapper`: it mounts a host-side mouse interface, continuously requests reports, and forwards them through a mouse HID device. It is still only a diagnostic/reference scaffold for M305. It declares one mouse-only device report (no Shift keyboard interface), casts input directly to `hid_mouse_report_t`, filters only X/Y, does not inspect the input report length or ID, and sends without waiting/checking the device interface's readiness. Use it for the host mount/receive flow, then add descriptor-aware decoding, queueing, the composite mouse+keyboard output, and readiness handling. The `hid_remapper` `setup1()/loop1()` split remains a useful dual-role/core arrangement; it is not the right mouse data path.

For initial receiver verification, log each mounted HID interface's protocol and the available report descriptor, then report length and raw bytes for motion, wheel, and tilt. This confirms the actual layout before relying on field mapping or promising full pass-through. Preserve report ID, X/Y, buttons, vertical wheel and horizontal pan in the relay whenever those fields are present.
